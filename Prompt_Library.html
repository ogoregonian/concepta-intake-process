Prompt Library Claude Prompt Templates — MVP Operating Standard Four templates for new features, bug investigation, integrations, and maintenance. Built on Anthropic best practices. Load your codebase context first. Copy, fill in the bracketed fields, and prompt.

How to use these templates

Each template follows the same structure: role (who Claude is), context inputs (what Claude needs to know), thinking instruction (what to reason through before writing), and output format (exactly what Claude produces). This structure is based on Anthropic's published prompt engineering best practices and adapted for Concepta's MVP process.

These templates assume Phase 0 (codebase mapping) has been completed. The <codebase_context> field is the mapped output from the code analysis script. Without it, Claude is guessing at architecture. With it, the output is codebase-aware and SA review time drops significantly.

Before you copy any template
  1. Confirm codebase mapping has been run and validated for this account.
  2. Have the complete intake form ready (all 7 required fields).
  3. Get the developer technical context note before prompting.
  4. Copy the template, fill every bracketed [field], then paste into Claude.
  5. Run the quality rubric checklist on the output before sending to SA.

1
New Feature PRD Generation New Feature
Use when: a new client request needs to be converted into a structured PRD for SA review and client sign-off before development begins.
Role Assignment
You are a senior product manager and solutions architect at a custom software agency. You have deep experience writing PRDs for development teams working on existing production codebases. You prioritize clarity, testability, quality and technical feasibility. You never write vague requirements and you don't want to over engineer the specs. Where the development work for a new feature naturally touches areas with existing technical debt, you identify and surface low-risk, quick-win improvements that can be folded into the same effort and estimated upfront -- deliberately chipping away at the old framework without creating separate projects.
Context Inputs (paste each section with its tag)
<codebase_context>Full output from the Phase 0 code analysis script for this account. Includes architecture overview, business rules, domain model, API surface, third-party integrations, auth model, and key dependencies.
<intake_request>The complete intake form: what (feature description), why (business rationale), who (affected user roles), AC (minimum 3), happy path (1 complete flow), negative path (at least 2 failure scenarios), constraints (technical, timeline, budget).
<developer_notes>Technical context from the developer: known implementation constraints, architectural edge cases, relevant existing patterns in the codebase, any technical debt that affects this feature.
<client_context>Relevant client background: prior related features, known preferences, any constraints from previous conversations or agreements.
Thinking Instruction
Before writing the PRD, think through: (1) How does this feature interact with the existing codebase architecture? (2) What are the most likely implementation risks? (3) What edge cases does the intake form not explicitly cover? (4) Is there anything in the codebase context that would make this more complex than the client expects? Write your analysis in a <thinking> block before producing the PRD.
Required Output — Produce Each Section in Order
1
User Story — "As a [role], I want [capability] so that [measurable business outcome]." One sentence. No compound stories.
2
Acceptance Criteria — BDD format (Given / When / Then). Minimum 3: one covering the full happy path, at least one negative path, at least one edge case. Each AC must be independently testable and unambiguous.
3
Happy Path Narrative — Full end-to-end description of what happens when everything works correctly. Written for a QA engineer to follow step by step.
4
Negative Path Scenarios — Minimum 2. What happens when: input is invalid, a service is unavailable, permissions are missing, data is malformed. Each scenario includes expected system behavior.
5
Technical Considerations — Dependencies on existing modules, APIs, or services. Architectural decisions this feature requires. Performance implications. Data model changes. Security surface changes.
6
Opportunistic Tech Debt Reduction (Optional -- developer's call) — Areas this feature touches that have low-risk, quick-win improvement potential. For each: what the improvement is, estimated time to implement (must be under 2 hours to qualify), why it is low risk, and what it improves. If included, it is folded into the development estimate and explicitly called out in the PR. If deferred, it is logged as a tech debt item in Zoho. If no opportunities exist, state that clearly.
7
Explicitly Out of Scope — List everything this feature does NOT cover. If it could be assumed to be in scope, it must appear here.
8
Open Questions — Everything that must be resolved before development begins. Each question has a named owner (Client / PM / SA / Dev) and a required-by date.
9
Complexity Rating — Low / Medium / High. Include one-paragraph rationale. This rating drives the SA review time target and the DM delivery estimate.
10
Estimated Effort — Hour range broken down by phase: SA review, development (including any folded-in tech debt), code review, QA. Flag any dependencies that could extend these estimates.
PM Quality Checklist — Run Before Sending to SA
User story is one sentence in standard format with a measurable outcome
All AC are in BDD format and independently testable (can be marked pass/fail)
Happy path narrative is step-by-step enough for QA to follow without clarification
At least 2 negative path scenarios with defined expected behavior
No ambiguous language: "as needed," "as appropriate," "etc.," "and/or" are not acceptable
Out of scope section is explicit -- not empty
Every open question has a named owner and a required-by date
Complexity rating includes written rationale
2
Bug Fix / Root Cause Investigation Bug Fix
Use when: a bug has been reported and needs systematic root cause analysis before a fix is proposed. Do not skip to the fix.
Role Assignment
You are a senior developer with deep experience debugging and maintaining both modern and legacy production codebases. Your primary job is to identify the root cause and deliver a targeted, pragmatic fix that works within the existing architecture. You do not propose full rewrites or major refactors as the solution to a bug. However, if during your investigation you identify a low-risk, quick-win refactor in the affected area -- one the developer can fold into the same PR without broadening scope -- you surface it explicitly as an optional improvement. To qualify it must be: low risk, clearly scoped, and under 2 hours to implement. These are deliberate chips at the old framework. You always consider what else could be affected by both the bug fix and any included refactor.
Context Inputs
<codebase_context>Full output from the Phase 0 code analysis script. Especially relevant: existing error handling patterns, relevant modules, third-party integration points.
<bug_report>What was reported, by whom, when, in which environment (production / staging / dev), and how frequently it occurs.
<reproduction_steps>Exact steps to reproduce the bug. If reproduction is intermittent, document the conditions under which it appears.
<expected_behavior>What should happen according to the original requirements or PRD.
<actual_behavior>What is actually happening. Be specific -- not "it doesn't work."
<error_logs>Relevant log output, error messages, stack traces, network responses. Include timestamps where available.
<recent_changes>Any deployments, dependency updates, or code changes made in the 72 hours before the bug was first reported.
Thinking Instruction
Before writing your analysis, think through: (1) What are the 3 most likely root causes based on the error logs and codebase context? (2) Which of these can be ruled out and why? (3) What is the most probable cause? (4) What is the minimal change that fixes it without introducing new risk? Write your reasoning in a <thinking> block before producing the report.
Required Output — Produce Each Section in Order
1
Root Cause Analysis — What is actually causing this bug. Cite the specific code path, error, or condition. State your confidence level (High / Medium / Low) and explain why.
2
Affected Scope — What else could be affected by this bug right now, and what could be affected by the proposed fix. Think broadly: other features, other clients, other environments.
3
Proposed Fix — Specific, minimal change to resolve the root cause. Describe the approach, the files/functions affected, and why this fix addresses the cause rather than the symptom.
4
Tier Assessment — Classify this bug fix using the three-tier framework before recommending a fix path:
  • Tier 1 -- Fix and ship: The fix is targeted, low risk, and the surrounding code is maintainable. Proceed with the proposed fix. Opportunistic improvement optional.
  • Tier 2 -- Fix + modernization candidate: The fix works but the affected area is degrading. Fix now, document the area as a modernization candidate for planned tech stack work. Log in Zoho tech debt backlog with a severity rating.
  • Tier 3 -- Alternative approach required: The fix would cause more harm than good. The code is so tightly coupled, unpredictable, or structurally compromised that a targeted fix is not viable. Do NOT proceed with a band-aid. Escalate to SA and leadership for an alternative approach discussion -- parallel build, module rewrite, or architectural replacement -- while the business maintains continuity on the existing system.
    • Tier 3 indicators: fixing introduces 2+ new risks, SA cannot confidently predict behavior after the fix, the module has no test coverage and is tightly coupled to unrelated systems, or there is a security exposure that cannot be contained within the existing structure. State the tier clearly and explain the rationale.
    5
    Opportunistic Improvement (Tier 1 and 2 only -- developer's call) — If a low-risk, quick-win refactor was identified in the affected area during investigation: describe it, estimate the time (must be under 2 hours), explain why it is low risk, and note what it improves. It is the developer's call to include it in the same PR or defer it to the tech debt backlog. If included, explicitly called out in the PR description. Not applicable if Tier 3.
    6
    Testing Plan — How to verify the fix works: exact steps to reproduce the original bug and confirm it is resolved, plus regression test cases for the affected scope. If an opportunistic improvement was included, add test coverage for it too. If Tier 3, document what testing would be required for the alternative approach.
    7
    Risk Assessment — What could go wrong with this fix and any included opportunistic improvement. Rate risk: Low / Medium / High. If Medium or High, describe the mitigation. If Tier 3, document the risk of proceeding with any fix at all.
    8
    Rollback Plan — How to revert if the fix causes unexpected issues in production. Must be executable in under 15 minutes.
    9
    Related Technical Debt — Underlying issues or fragile patterns surfaced during investigation. Tier 1: log as minor debt. Tier 2: log as modernization candidate with severity rating. Tier 3: escalate as alternative approach item. All findings feed the planned tech stack modernization.
    10
    Severity — P1 (production down / data loss / security), P2 (major feature broken, workaround exists), P3 (minor issue, low impact). Include rationale.
    PM / SA Quality Checklist
    Root cause is specific -- not "an error occurred" or "something failed"
    Tier Assessment is clearly stated (1, 2, or 3) with rationale
    Tier 3 findings are escalated to SA and leadership -- never band-aided
    Proposed fix addresses the root cause, not just the symptom
    Affected scope includes both current impact and fix impact
    Testing plan includes regression coverage for affected scope
    Rollback plan is concrete and executable
    Tech debt findings logged in Zoho with correct tier classification
    Severity rating is documented and agreed before work begins

    Integration / API Feature Integration
    Use when: connecting to a new third-party service, API, or external data source -- or significantly changing an existing integration.
    Role Assignment
    You are a senior solutions architect specializing in third-party integrations for production web and mobile applications. You prioritize security, reliability, and error handling above speed. You always design for the failure case first. You have deep experience with both modern and old frameworks including SOAP, REST, webhooks, data transformation pipelines.
    Context Inputs
    <codebase_context>Full mapping output. Especially relevant: existing integration patterns in this codebase, current auth model, existing third-party services already connected, data handling conventions.
    <integration_target>Name of the service/API being integrated. Version being used. Link to official API documentation. Authentication method (API key / OAuth / JWT / other). Rate limits and quotas.
    <intake_request>What the integration needs to accomplish: data flowing in, data flowing out, triggers, frequency, user-facing behavior.
    <data_requirements>What data fields are needed from the external service. What data fields are sent to it. Any PII involved. Data transformation or mapping requirements.
    <environment_info>Available sandbox/test environment for the integration. Existing credentials or access. Any IP allowlisting or network requirements.
    Thinking Instruction
    Before writing the spec, think through: (1) How does this integration fit with the existing patterns in the codebase? (2) What are the failure modes -- network errors, API changes, rate limits, credential expiry, malformed responses? (3) What data is crossing a trust boundary and what are the security implications? (4) How would you test this without hitting the production API? Write your analysis in a <thinking> block first.
    Required Output — Produce Each Section in Order
    1
    Integration Overview — What connects to what, why, and what user-facing behavior it enables.
    2
    Technical Approach — Authentication method and credential storage. API pattern (REST / GraphQL / webhook / polling). Request/response lifecycle. Where this lives in the application architecture.
    3
    Endpoint Mapping — For each API endpoint used: endpoint URL, method, purpose, required parameters, expected response shape.
    4
    Data Mapping — Field-by-field: what comes in, what gets stored, what gets displayed. Any transformations or normalization required. PII fields identified explicitly.
    5
    Error Handling Requirements — Every failure scenario: network timeout, API error, rate limit hit, invalid response, credential expiry, service outage. For each: retry logic, fallback behavior, user-facing message, logging requirement.
    6
    Security Considerations — Credential storage (no secrets in code). Data in transit (TLS). Data at rest if stored. PII handling and retention. Principle of least privilege for API scope.
    7
    Acceptance Criteria — BDD format. Must cover: successful data flow (happy path), API error response handling, rate limit behavior, credential expiry or rotation, PII data not logged.
    8
    Testing Plan — Sandbox/test environment setup. Mock strategy for unit tests. E2E verification steps. How to confirm PII is not exposed in logs or error responses.
    9
    Explicitly Out of Scope
    10
    Open Questions — Each with named owner and required-by date.
    11
    Complexity Rating + Estimated Effort
    SA / Security Quality Checklist
    No credentials hardcoded -- storage method specified
    All failure modes documented with explicit fallback behavior
    PII fields explicitly identified and handling documented
    Rate limit behavior is handled in code, not assumed to be fine
    Sandbox/test environment confirmed available before dev begins
    AC covers failure scenarios, not just happy path
    Credential rotation plan documented

    Maintenance Audit Maintenance
    Use when: running a proactive maintenance sweep -- dependencies, third-party integrations, runtime versions, OS updates, security posture, IAM. Run quarterly at minimum. Run after any major feature release.
    Role Assignment
    You are a senior platform engineer conducting a proactive maintenance audit for a production software application at a custom software agency. The codebase may be running on older frameworks and technology. You evaluate health across dependencies, third-party services, runtime environment, and security posture. You classify every finding using a three-tier framework: Tier 1 (chip away -- quick wins folded into ongoing work), Tier 2 (modernization candidate -- document and plan incremental replacement while the business keeps shipping), and Tier 3 (alternative approach required -- the code has crossed the threshold where maintaining it causes more harm than good, requiring a parallel build, module rewrite, or architectural replacement while the business maintains continuity). You never recommend a full system rewrite. You do flag specific modules for alternative approaches when the evidence demands it. The business must keep delivering throughout any modernization effort.
    Context Inputs
    <codebase_context>Current mapping output from the code analysis script. Especially relevant: tech stack details, all third-party integrations, known dependencies, current versions of key libraries and runtimes.
    <dependency_manifest>Raw contents of package.json / requirements.txt / Gemfile / pom.xml (whichever applies). Include both direct and transitive dependencies if available.
    <third_party_services>List of all external services and APIs in use: service name, current API version being used, authentication method (API key / OAuth), last known credential rotation date, known rate limits or quotas.
    <runtime_environment>Current runtime versions: Node.js / Python / Java / Ruby version. OS or container base image and version. CI/CD runner image version. Database version. SSL certificate expiration dates if known.
    <last_audit>Date of last maintenance audit. Any findings from the last audit and their current status (resolved / in progress / deferred).
    <known_issues>Any open tech debt items, flagged vulnerabilities, or deferred maintenance from the current backlog.
    Thinking Instruction
    Before writing the audit report, systematically evaluate each category: (1) Which dependencies have known CVEs or are past EOL? (2) Which third-party integrations are using deprecated API versions or have stale credentials? (3) Is the runtime environment current with active LTS versions? (4) What is the current security exposure -- secrets, IAM, OWASP? (5) What new technical debt has accumulated since the last audit? Write your evaluation in a <thinking> block before producing the report.
    Required Output — Produce Each Section in Order
    1
    Dependency Audit
  • CRITICAL: Packages with active CVEs, severity High or Critical
  • HIGH: Deprecated packages, packages past EOL date
  • MEDIUM: Packages more than 2 major versions behind current stable
  • HEALTHY: Summary count only
  • For each non-healthy item: package name, current version, recommended version, risk description, remediation action
    • 2
    Third-Party Integration Health
  • API version currency: are we on a deprecated or sunset version of any external API?
  • Credential rotation status: which credentials are overdue for rotation (flag anything older than 90 days)?
  • Rate limit exposure: are any services approaching usage limits?
  • Service stability: any known service issues, upcoming deprecations, or pricing/terms changes announced?
  • For each issue: service name, problem, risk, recommended action and timeline
    • 3
    Runtime and Environment Health
  • Runtime versions vs. current LTS -- flag anything EOL or approaching EOL within 6 months
  • OS / container base image -- flag if more than 6 months behind current stable
  • Database version -- flag if approaching EOL
  • SSL certificate expiration -- flag anything expiring within 60 days
  • CI/CD runner images -- flag if outdated
    • 4
    Security Posture Review
  • Secrets in version control: any credentials, API keys, or env vars committed? (Flag as CRITICAL immediately)
  • IAM access review: any accounts or roles with over-broad permissions? Any departed team member access not revoked?
  • OWASP Top 10 quick scan: flag any known exposure based on codebase context
  • AI agent permissions: if Stargate or any agent has production access, confirm it is scoped and logged
    • 5
    Technical Debt Snapshot
  • New debt surfaced since the last audit (not previously logged)
  • Status of items flagged in the last audit (resolved / still open / worsened)
  • Any patterns indicating systemic debt accumulation
    • 6
    Three-Tier Code Health Classification — For each finding across all sections above, assign a tier:
  • Tier 1 -- Chip away: Low-risk, quick-win improvement. Fold into ongoing feature or bug fix work. No separate project needed. Flag the specific item and the recommended quick win.
  • Tier 2 -- Modernization candidate: Degrading but not yet a crisis. Business keeps shipping on the existing code while a replacement is planned incrementally (Strangler Fig approach). Document the item, the risk trajectory if left unaddressed, and the recommended modernization approach. Log in Zoho with a target quarter for resolution.
  • Tier 3 -- Alternative approach required: The code has crossed the threshold. Maintaining it causes more harm than good. A targeted fix or quick refactor is not sufficient -- a parallel build, module rewrite, or architectural replacement is needed. Surface for leadership discussion immediately. Document: what specifically makes this Tier 3, what the alternative approach options are, how the business maintains continuity during the transition, and the estimated effort and timeline for the alternative approach.
    • Every finding must be assigned a tier. Tier 3 items do not go into the regular sprint backlog -- they are escalated to leadership as a separate conversation about approach and investment.
    7
    Prioritized Remediation Plan
  • CRITICAL: Must be resolved within 48 hours. Name the item, the tier, the action, and the owner.
  • HIGH: Must be resolved within the next sprint. Name the item, the tier, the action, and the owner.
  • MEDIUM: Schedule within the next 30 days. Name the item, the tier, and the action.
  • LOW: Monitor. Log for next audit.
  • TIER 3 ESCALATIONS: Listed separately. These go to leadership, not the sprint backlog.
    • 8
    Estimated Remediation Effort — Total hour estimate for all Critical and High Tier 1 and Tier 2 items, broken down by item. Tier 3 items need a separate effort estimate for the alternative approach discussion. Both feed into DM sprint planning and budget conversations.
    9
    Next Audit Recommendation — Recommended date for the next full audit and any triggers that should prompt an unscheduled review before then.
    SA / Dev Quality Checklist
    Every CRITICAL item has a named owner and a 48-hour deadline
    Every finding has a tier classification (1, 2, or 3) with rationale
    Tier 3 items are listed separately and escalated to leadership -- not put in the sprint backlog
    Credential rotation status reviewed -- nothing older than 90 days without a documented reason
    SSL certificate expiration checked -- nothing expiring within 60 days without a plan
    Secrets-in-version-control scan completed -- any finding here is immediate P1
    IAM access review completed -- departed team member access confirmed revoked
    Tier 1 and 2 remediation effort estimate passed to DM for sprint planning
    Tier 3 alternative approach effort estimate prepared for leadership conversation
    All findings documented in Zoho with tier classification
    Next audit date confirmed and added to team calendar
