MVP Operating Standards

How We Operate -- The Rules That Make This Work

Nine standards that govern every step of the MVP process. Each one has a clear owner, a defined gate, and an exception path. These are not guidelines -- they are the process. Skipping a gate does not save time; it moves the cost downstream where it is more expensive to fix.

1
Codebase Mapping
Run once before the first AI-assisted PRD on any codebase. Full re-map triggers: major framework upgrade, new service or external integration added, significant database schema change, security refactor. Incremental re-map (affected modules only): after any significant feature touching a specific area. Scheduled: quarterly as part of the maintenance audit, and before working on any module dormant 6+ months. Concurrent self-validation pass required. Output lives in the repo /docs folder, linked from Zoho.
Owner
Assigned dev per account. SA confirms mapping is current and sufficient before PRD generation begins on any codebase area.
2
Intake Completeness Gate
Seven fields required before PM can prompt Claude -- no exceptions: What (feature description), Why (business rationale), Who (affected user roles), AC (minimum 3), Happy path (1 complete flow), Negative path (at least 2 failure scenarios), Constraints (technical, timeline, budget). If any field is missing, PM returns to client before proceeding. For Medium or High complexity tickets: PM + SA do a brief 15-minute pre-screen of the intake together before Claude is prompted -- confirming technical assumptions are sound before generating a PRD that may need significant rework.
Hard Gate
Partial intakes do not advance. For complex tickets, SA pre-screens the intake alongside PM before Claude is prompted. Human-in-the-loop validation at the point where it costs the least.
3
Prompt Library + PRD Template
Three core prompt templates: new feature, bug fix, integration/API. Each template specifies: context to load (codebase mapping + complete intake + dev technical note), what to ask Claude to produce (user story, BDD AC, happy/negative path narratives, technical considerations, explicit out-of-scope section, open questions), and a quality checklist to run before sending to SA. Templates live in Notion, maintained by PM + dev, reviewed after every project.
Owner
PM + Dev jointly. PM runs the prompt; dev contributes the technical context note before PM starts.
4
PRD Quality Rubric
Before SA touches a PRD, PM checks six things: (1) User story in standard format. (2) Minimum 3 AC in BDD Given/When/Then format covering happy path, at least 1 negative path, at least 1 edge case. (3) Explicit out-of-scope section. (4) No ambiguous language ("as needed," "etc.," "as appropriate"). (5) Technical dependencies identified. (6) Open questions flagged. If any item fails, PM revises before SA review begins.
Hard Gate
PRD does not go to SA if it fails the rubric. PM owns the quality check -- not SA.
5
SA Review Protocol
PM and SA review the Claude-generated PRD together in a single session -- PM validates business accuracy, SA validates technical feasibility. Both sign off before it goes to the client. Review time targets: 30 min Low / 2 hours Medium / half-day High. SA assigns complexity. Sign-off is written Zoho comment -- not verbal. If SA rejects, written feedback required and re-review within 24 hours.
Owner
Joint: PM + SA. Reviewing together catches both business and technical gaps in one pass. SA's complexity rating drives the DM's delivery estimate.
6
Client Sign-off Protocol
PRD sent via agreed channel. Client has 48 hours to respond. Approval must be explicit -- silence is not approval. If client requests changes: minor UI feedback = dev fixes without reopening PRD. Functional gap = new ticket, new PRD. Scope change = budget conversation before anything else. Written client approval must be documented in Zoho before development begins.
Hard Gate
No development begins without written client approval in Zoho. This is the single most important gate in the MVP process.
7
Development with Claude
Branch created from the PRD ticket (branch name includes ticket number). PRD loaded as context at session start. Developer reviews and approves every Claude output before committing. Developer is responsible for all committed code -- Claude is a tool, not an author. Developer testing runs in parallel with the build, not after. No PR opened without developer having validated the happy path locally.
Owner
Developer. Dev testing happens during the build -- not as a separate phase after code is "done."
8
Demo Protocol
Demo is a working feature in staging -- not a mockup or screenshot. PM presents via screen share or async Loom. Client has 24 hours to respond: Approved / Change Requested / Question. Change Requested: minor UI = dev fixes without reopening PRD; functional gap = new ticket with new PRD; scope change = budget conversation first. Demo approval documented in Zoho before QA begins.
Hard Gate
QA does not begin until client demo approval is documented. Demo feedback is not a QA issue -- it is a requirements issue.
9
QA Completion Criteria
Feature testing: every PRD AC marked pass/fail in Zoho. Regression testing: core user flows validated across all affected areas. Bug severity: P1 blocks release, P2 requires fix before release, P3 is post-release. No P1 or P2 bugs open at time of release. QA sign-off is a written Zoho status change -- not verbal. Both feature and regression testing are required at every release.
Owner
QA. Sign-off must reference the PRD ticket. No production deploy without documented QA pass.

Implementation Sequence -- How to Get This Live

1
Ratify these 9 standards with the full team
One meeting. Walk through each standard, surface objections, agree on any modifications. The team needs to own this -- not just be told about it. Document the ratified version in Notion.
Owner: Full team alignment session
2
Build the 3 core prompt templates
PM + dev in one working session. Template 1: new feature. Template 2: bug fix. Template 3: integration/API. Each template includes context loading instructions, required inputs, expected Claude output format, and quality checklist. Store in Notion.
Owner: PM + Dev (1 session)
3
Choose the first dogfood account and run codebase mapping
Select one account to run this process end-to-end first. Run the code analysis script. Complete the concurrent self-validation pass. Confirm SA reviews and approves the mapping output before using it for PRD generation.
Owner: Dev + SA
4
Run the first end-to-end PRD generation cycle
Take a real pending request from the dogfood account. PM runs the Claude prompt using the template. SA reviews the output. Document how long SA review took vs. current state baseline. Capture what the prompt template missed.
Owner: PM + SA
5
Iterate the prompt template based on SA feedback
SA documents what the first PRD got wrong or missed. PM + dev update the prompt template to address those gaps. Run a second PRD generation pass. Repeat until SA review time is consistently under the target thresholds.
Owner: PM + Dev + SA
6
Complete one full cycle end-to-end on the dogfood account
PRD generation → SA review → client sign-off → dev with Claude → code review → demo → QA → production. Document the time at each stage. Compare against current state baseline. This is your proof of concept and your team alignment moment.
Owner: Full team
7
Roll out to the next account after one validated cycle
Do not expand to all accounts at once. One validated cycle proves the process works. Run codebase mapping on the next account. Apply the refined prompt templates. The process scales -- but only after it has been validated end-to-end on one account first.
Owner: PM + Dev
